### 1. Il "Reasoning" serve all'Agente 2 per non sbagliare (Chain-of-Thought)

Quello che vedi non è solo "chiacchiera". È il meccanismo di **Chain-of-Thought (CoT)**.
Se tu forzassi l'Agente 2 a restituire *solo* la lista JSON `['Fabbricati', 'FabbricatiVincoli']` senza permettergli di generare prima il testo di ragionamento, **la precisione della selezione crollerebbe**.

* Con 4 tabelle è facile.
* Con **28 tabelle**, il rischio che selezioni una tabella con un nome simile ma sbagliata è alto. Il ragionamento riduce questo rischio.

### 2. Cosa serve *davvero* all'Agente 3 (SQL Generator)?

* Intento
* Entità

### Il Flusso Corretto (Best Practice)

Tra l'Agente 2 (Selector) e l'Agente 3 (Generator) deve succedere una cosa tecnica:

1. **Agente 2:** Esce con `selected_tables=['Fabbricati', 'FabbricatiVincoli']` e il `reasoning`.
2. **Tool/Funzione intermedia:** Prende quei nomi e va nel DB (o in `src.database`) a recuperare il `CREATE TABLE` completo **solo** per quelle 2 tabelle.
3. **Agente 3:** Riceve in input:
* La domanda utente.
* Il `reasoning` dell'Agente 2 (usalo come "suggerimento" o "piano d'azione").
* **Il DDL delle tabelle scelte** (questo è obbligatorio).

La risposta breve è: **No, non farlo. Sarebbe un errore architettonico.**

Se dai quei tool all'Agente 3, lo trasformi in un "Agente 2 bis". Noterai infatti che il codice che hai incollato ha come output `TableSelectionResult` (selezione tabelle), non codice SQL.

### Perché è sbagliato dare i tool all'Agente 3?

L'Agente 2 ha **già deciso** quali tabelle servono (`selected_tables`).
Se all'Agente 3 dai il tool `get_schema_tool`, lo costringi a fare questo giro inutile:

1. Riceve i nomi delle tabelle.
2. L'LLM deve "pensare": *"Ah, devo chiamare il tool per avere lo schema"*.
3. Ferma l'esecuzione -> Chiama Python -> Rientra nell'LLM.
4. Scrive l'SQL.

È lento e spreca token.

### La Soluzione Migliore: "Context Injection"

Dato che i nomi delle tabelle li hai già (nello `state['selected_tables']`), puoi recuperare il DDL (lo schema) **direttamente via codice Python** dentro il nodo del grafo, *prima* di chiamare l'LLM.

L'Agente 3 deve trovare la "pappa pronta": lo schema deve essere già nel suo prompt.

Ecco come scrivere il nodo **SQL Generator** in modo efficiente nel tuo file `agent.py` (o dove definisci i nodi), usando il `DatabaseManager` direttamente senza passare per i tool dell'LLM.

```python
# In agent.py

from langchain_core.prompts import ChatPromptTemplate
from src.database import DatabaseManager 
from src.models import AgentState

# ... configurazione llm ...

async def run_sql_generator(state: AgentState):
    print("✍️ (SQL Generator) Preparazione contesto e generazione query...")
    
    # 1. Recupera i nomi delle tabelle decise dall'Agente 2
    selected_tables = state.get("selected_tables", [])
    
    if not selected_tables:
        return {"error": "Nessuna tabella selezionata dall'Agente 2."}

    # 2. CONTEXT INJECTION (Il trucco per evitare i tool)
    # Usiamo la classe Python direttamente per estrarre il testo DDL.
    # Non serve che l'LLM "decida" di farlo, lo facciamo noi per lui.
    db_manager = DatabaseManager(state["db_path"])
    ddl_context = ""
    
    try:
        for table in selected_tables:
            # Recupera il CREATE TABLE per ogni tabella scelta
            ddl = db_manager.get_table_ddl(table)
            ddl_context += f"-- Schema per {table}:\n{ddl}\n\n"
    except Exception as e:
        return {"error": f"Errore nel recupero DDL: {str(e)}"}

    # 3. Costruzione del Prompt per l'SQL Generator
    # Gli diamo tutto: DDL preciso, Ragionamento precedente, Domanda.
    
    # Recuperiamo il ragionamento dell'Agente 2 (l'ultimo messaggio)
    last_reasoning = state["messages"][-1].content if state["messages"] else "Nessun ragionamento disponibile."

    generator_prompt = """
    Sei un esperto sviluppatore SQL (Dialetto SQLite).
    Il tuo compito è scrivere una query SQL corretta ed efficiente per rispondere alla domanda dell'utente.
    
    ### SCHEMA DEL DATABASE (DDL)
    Qui trovi la struttura ESATTA delle tabelle da usare:
    {ddl_context}
    
    ### ANALISI PRELIMINARE (Dal Data Engineer)
    Segui questo piano logico per i JOIN e i filtri:
    {reasoning}
    
    ### DOMANDA UTENTE
    {query}
    
    ### REGOLE
    1. Restituisci SOLO il codice SQL puro.
    2. Non mettere markdown (```sql).
    3. Usa i nomi delle colonne ESATTI forniti nel DDL qui sopra.
    4. Se serve un JOIN, controlla bene le Foreign Key nel DDL.
    """
    
    prompt_template = ChatPromptTemplate.from_template(generator_prompt)
    chain = prompt_template | llm
    
    # 4. Generazione
    print(f"   Generazione SQL su {len(selected_tables)} tabelle...")
    response = await chain.ainvoke({
        "ddl_context": ddl_context,
        "reasoning": last_reasoning,
        "query": state["user_query"]
    })
    
    generated_sql = response.content.strip()
    
    # Pulizia eventuale markdown (se l'LLM disubbidisce)
    generated_sql = generated_sql.replace("```sql", "").replace("```", "").strip()
    
    return {
        "generated_sql": generated_sql,
        "messages": [f"SQL Generato:\n{generated_sql}"]
    }

```

### Perché questa soluzione è superiore?

1. **Deterministica:** Non rischi che l'Agente 3 "decida" di non guardare lo schema. Glielo sbatti in faccia nel prompt.
2. **Veloce:** Risparmi 1 round-trip di chiamata tool.
3. **Pulita:** L'Agente 3 fa una cosa sola: Traduzione da (Testo + Schema) -> SQL.

### Quando servirebbero i tool all'Agente 3?

L'unico caso in cui daresti i tool all'Agente 3 è se volessi implementare un meccanismo di **Self-Correction (Auto-guarigione)**:

* L'Agente 3 scrive la query.
* Provi a eseguirla -> Errore "Colonna non trovata".
* L'Agente 3 riceve l'errore e allora *lì* potrebbe usare un tool `list_columns` per capire come si chiama davvero la colonna.

Ma per ora, nel flusso "Standard", l'approccio **Inject DDL via Python** è la best practice assoluta.

async def run_sql_generator(state: AgentState):
    print("✍️ (SQL Generator) Recupero DDL e generazione query...")
    
    # 1. Recupera tabelle selezionate
    selected_tables = state.get("selected_tables", [])
    if not selected_tables:
        return {"error": "Agente 2 non ha selezionato nessuna tabella."}

    # 2. INJECT DDL (Recupero schema puntuale via Python)
    try:
        db_manager = DatabaseManager(state["db_path"])
        ddl_context = ""
        for table in selected_tables:
            # Recupera il CREATE TABLE pulito
            ddl = db_manager.get_table_ddl(table)
            ddl_context += f"-- Tabella: {table}\n{ddl}\n\n"
    except Exception as e:
        return {"error": f"Errore nel recupero DDL dal DB: {str(e)}"}

    # 3. Costruzione Prompt
    # Recuperiamo l'ultimo messaggio che contiene il ragionamento dell'Agente 2
    # (assumiamo sia l'ultimo aggiunto alla lista messages)
    last_message = state["messages"][-1]
    reasoning_context = last_message if isinstance(last_message, str) else last_message.content

    generator_prompt = """
    Sei un esperto sviluppatore SQL per database SQLite.
    Il tuo compito è convertire una richiesta in linguaggio naturale in una query SQL precisa ed eseguibile.

    ### 1. SCHEMA DEL DATABASE (DDL ESATTO)
    Usa SOLO le tabelle e le colonne definite qui sotto:
    {ddl_context}

    ### 2. PIANO LOGICO SUGGERITO (Dal Data Analyst)
    Segui questo ragionamento per JOIN e filtri:
    {reasoning}

    ### 3. RICHIESTA UTENTE
    {query}

    ### REGOLE OBBLIGATORIE:
    - Restituisci SOLO il codice SQL puro (niente markdown ```sql, niente spiegazioni).
    - Usa sintassi compatibile con SQLite.
    - Se usi JOIN, assicurati che le colonne esistano nel DDL fornito.
    """

    prompt_template = ChatPromptTemplate.from_template(generator_prompt)
    chain = prompt_template | llm

    try:
        # 4. Invocazione LLM
        response = await chain.ainvoke({
            "ddl_context": ddl_context,
            "reasoning": reasoning_context,
            "query": state["user_query"]
        })
        
        raw_sql = response.content.strip()
        
        # Pulizia base (rimozione markdown se presente)

            "generated_sql": clean_sql,
